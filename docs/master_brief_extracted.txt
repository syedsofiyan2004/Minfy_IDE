MINFY IDE — MASTER PROJECT BRIEF
You are working on a serious internal engineering product called Minfy IDE.
This is NOT intended to be a quick AI wrapper, demo-only prototype, hackathon project, or AI-generated “slop” application.
The objective is to gradually build a reliable, polished, browser-first intelligent development environment that can later be released internally at Minfy and potentially open-sourced.
The application must prioritize:
Genuine usefulness
Excellent UI/UX
Reliability
Maintainable architecture
Security
Low AI/token cost
Cross-platform compatibility
Provider independence
Extensibility
Simplicity for developers

CORE ARCHITECTURAL PRINCIPLE
Separate the system into clearly defined layers.
Conceptually:
Browser IDE↓Local Runtime↓Workspace / Repository Intelligence↓Context Compiler↓Task Planner↓AI Scheduler↓Provider Registry↓AI Providers / MCP / Local Models / Enterprise Models
Do NOT tightly couple the user interface directly to Claude, OpenAI, Bedrock, or any individual provider.
All providers must eventually sit behind internal interfaces/adapters.

BROWSER-FIRST ARCHITECTURE
The initial product is browser-first.
However, it must be capable of working on a local project.
Example:
cd C:\Projects\my-app
minfy .
Expected flow:
CLI resolves the workspace path.
CLI starts or connects to the Minfy local runtime.
Runtime registers the workspace.
Runtime starts the local Minfy web application if necessary.
Browser opens automatically.
Browser connects to the local runtime.
Project appears in Minfy IDE.
User can browse/edit files.
Terminal commands run on the local machine inside the workspace.
Project files remain local unless explicitly required by an external AI provider.
The browser is the UI.
The local runtime handles privileged machine operations.
Do not try to make the browser itself execute arbitrary host commands.

SECURITY PRINCIPLES
Security must be designed into the architecture.
Important future principles:
never expose raw provider secrets to the browser unnecessarily
keep sensitive credentials in the local runtime
scope workspace access
prevent arbitrary path traversal
validate terminal/workspace boundaries
never automatically execute commands from cloned repositories
require approval for dangerous operations
treat free/unknown AI endpoints differently from trusted enterprise providers
support future data classification and trust levels

DEVELOPMENT PHILOSOPHY
This project MUST be built incrementally.
Never attempt to implement the whole architecture in one response/task.
Each milestone must:
introduce a small number of capabilities
work end-to-end

remain understandable

TESTING PHILOSOPHY
We want working software, not test bureaucracy.
Testing should prioritize critical behavior.
Do NOT create extremely strict testing gates that block development over trivial implementation details.
Avoid:
fragile snapshot tests
testing cosmetic implementation details
artificial 100% coverage requirements
massive mock architectures
tests coupled to internal function names
excessive unit tests for trivial code
huge lint/style rule sets that prevent iteration
Prefer:
smoke tests
integration tests
critical API tests
filesystem safety tests
workspace opening tests
save/read tests
terminal safety tests
regression tests for bugs actually encountered
A test should protect meaningful user behavior.

ERROR-HANDLING PHILOSOPHY
Do not hide errors.
Do not crash the whole IDE because one operation fails.
Show useful errors to users.
Example:
Bad:Error 500
Better:Unable to save src/app.ts.The file may have been changed or the workspace is no longer available.
Keep developer logs detailed while user-facing messages remain understandable.

IMPORTANT WORKING RULE
Before modifying code:
inspect the current repository
understand what already exists
identify the minimum necessary change
preserve existing working behavior
After modifying code:
run relevant checks
run the application when possible
inspect the actual user flow
fix real failures
summarize exactly what changed
identify any remaining known limitations
Never declare success only because code compiles.
The actual feature should work.

CHANGE CONTROL
Do not modify unrelated areas of the repository.
Do not perform large refactors unless they are necessary.
If architectural debt is discovered but unrelated to the current milestone, document it instead of silently rewriting the project.

WORKING STYLE
When given a milestone:
inspect repository
explain briefly what exists
identify implementation plan
implement
run relevant validation
fix discovered issues
review UX
summarize completed work
Do not continue into the next milestone automatically.
Stop after the requested milestone is genuinely complete.

MOST IMPORTANT RULE
A smaller feature that works properly is better than ten half-working features.
Minfy IDE must become useful through reliable vertical slices rather than a giant generated codebase.
